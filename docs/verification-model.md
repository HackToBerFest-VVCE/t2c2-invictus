# Invariant Verification & Findings Model

This document specifies the verification classification taxonomy, evidence requirements, and reporting model utilized by **Invariant**. It establishes formal rules for categorizing verification outcomes and preventing false positives or deceptive passes.

---

## 1. Principles of Verification Integrity

Verification platforms must maintain unwavering trust with engineering teams. The core philosophy of Invariant is grounded in three principles:

1. **Empirical Evidence Required**: A failure is only marked as confirmed when backed by a concrete, reproducible execution trace, assertion failure, or deterministic proof.
2. **Fail-Safe Inconclusive Reporting**: An unavailable, timed-out, or crashed check must **never** be reported as a passing check. "Untested" or "Unrunnable" is fundamentally different from "Verified".
3. **Strict Separation of AI Hypotheses from Truth**: Suggestions generated by AI models are advisory hypotheses. They must never fail a build or masquerade as verified bugs without dynamic sandbox reproduction.

---

## 2. Verification Status Taxonomy

Every check executed or evaluated by Invariant produces an outcome classified under one of the following six distinct statuses:

```
                                  +-------------------+
                                  | Check Scheduled   |
                                  +-------------------+
                                            |
                         +------------------+------------------+
                         |                                     |
               [Execution Attempted]                  [Tooling / Syntax Check]
                         |                                     |
          +--------------+--------------+                      +---------------+
          |              |              |                      |               |
     (Exit 0)       (Assertion     (Timeout /             (Rule Not       (AST / Rule
         |           Failed)       Environment Fail)      Supported)       Warning)
         v              v               v                      v               v
  VERIFIED_PASS  VERIFIED_FAILURE  CHECK_ERROR           UNSUPPORTED     STATIC_WARNING
                        ^
                        | (Reproduced by Runner)
                        |
                 AI_HYPOTHESIS
           (Speculative LLM Idea)
```

| Verification Status | Meaning | Empirical Evidence Required | Build Impact |
| :--- | :--- | :--- | :--- |
| **`VERIFIED_PASS`** | The invariant check executed completely and all assertions held true. | Clean exit code (`0`), passed assertions, zero unhandled exceptions. | Check Passes (`success`). |
| **`VERIFIED_FAILURE`** | An invariant violation was reproduced dynamically in the execution runner. | Concrete execution trace, failed assertion line, stdout/stderr error dump. | Check Fails (`failure`); blocks merge. |
| **`STATIC_WARNING`** | A static analysis rule flagged a structural pattern that may violate an invariant. | AST rule match, file path, line/column number, static rule identifier. | Warning (`neutral`); non-blocking. |
| **`AI_HYPOTHESIS`** | An AI model postulated an edge-case violation, but no test has reproduced it yet. | AI reasoning trace and postulated scenario; explicitly labeled as unverified. | Advisory (`neutral`); non-blocking. |
| **`CHECK_ERROR`** | The verification check could not complete due to infrastructure, missing tools, or timeouts. | Runner exit code, crash logs, OOM killer trace, or timeout notification. | Inconclusive (`neutral`/`action_required`). |
| **`UNSUPPORTED`** | The invariant specification contains directives not supported by the runner. | Parser diagnostic identifying unsupported grammar or missing test harness. | Informational notice. |

---

## 3. Why Unavailable Checks Must Never Be Reported as Passing

A dangerous anti-pattern in continuous integration is the "silent pass"—where a missing dependency, skipped test, or crashing test runner results in a green checkmark because no assertion failure was explicitly logged.

In Invariant:
* If a test runner times out after 300 seconds, the status is **`CHECK_ERROR` (Timeout)**.
* If a Docker runner fails to install dependencies, the status is **`CHECK_ERROR` (Environment Failure)**.
* If an invariant has no corresponding test harness implemented yet, the status is **`UNSUPPORTED`** or **`UNTESTED`**.

> [!CAUTION]
> Reporting an unexecuted or crashed check as `VERIFIED_PASS` creates a false sense of security that allows critical regressions to reach production. Invariant treats non-execution as an alertable event.

## 5. UI and GitHub Annotation Presentation

When Invariant delivers findings to developers, it surfaces them across multiple touchpoints with consistent formatting:

### 5.1 GitHub Pull Request Inline Annotation
```
[CRITICAL] Invariant Violation: INV-01
Line 142: services/inventory/service.py
Expected: item.available_stock >= 0
Actual:   item.available_stock was decremented to -3
Evidence: AssertionError in test_race_condition_stock (Exit Code: 1)
```

### 5.2 Dashboard Findings View
The web dashboard provides interactive filtering:
* Filter by status: `VERIFIED_FAILURE`, `AI_HYPOTHESIS`, `STATIC_WARNING`, `CHECK_ERROR`.
* Filter by severity: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `INFO`.
* One-click download of reproduction scripts (`reproduce.sh`) and container execution logs.

## 6. Verification Intelligence Engine (VIE) Post-Detection Taxonomy

To address the challenge of high false-positive rates from AI code reviewers, Invariant introduces the **Verification Intelligence Engine (VIE)** (`packages/verifier/intelligence_engine.py`). Rather than acting as a speculative scanner, the VIE operates as a **post-detection gatekeeper** that evaluates suspected issues against `INVARIANT.md` requirements and empirical reproduction evidence.

### 6.1 The 5-Tier Post-Detection Classification Model

| Status | Definition | Evidentiary Requirements | PR / Build Action |
| :--- | :--- | :--- | :--- |
| **`Reproduced`** | The suspected defect was conclusively reproduced in the isolated runner under documented conditions. | 1. Candidate reproduction test executed in isolated sandbox.<br>2. Exit code $\ne 0$.<br>3. Concrete assertion failure trace or crash captured (`ASSERTION_FAILURE`).<br>4. Verified against `INVARIANT.md` rules. | **BLOCK_PR** (Blocks PR merge, emits inline check annotations). |
| **`Strongly Supported`** | Multiple corroborating static and semantic signals support the finding, but dynamic reproduction was unavailable. | 1. Corroborated by `INVARIANT.md` rule mapping.<br>2. Confirmed untested test gap identified in target file.<br>3. Static structural signals align with suspected flaw. | **WARN_REVIEWER** (Non-blocking warning; alerts reviewers to high-risk untested paths). |
| **`Potential`** | The issue is logically plausible based on AI code analysis, but lacks dynamic reproduction or corroborating static proof. | 1. AI model postulated edge scenario.<br>2. No reproduction test has succeeded or test was not provided.<br>3. No concrete runtime evidence. | **ADVISORY_NOTICE** (Labeled as unverified AI hypothesis). |
| **`Inconclusive`** | The verification check could not establish validity due to environmental, infrastructure, or tooling errors. | 1. Runner timed out ($>300$s).<br>2. Process crashed or OOM killed (`TIMEOUT_OR_CRASH`).<br>3. Missing dependency or syntax error in test harness. | **FIX_HARNESS** (Prompts developer to fix test harness or execution environment). |
| **`False Positive`** | Evidence establishes that the suspected issue is invalid or non-reproducible. | 1. Candidate reproduction test executed cleanly with exit code `0` (`PASSING`).<br>2. Invariant assertions held true under empirical execution.<br>3. Code inspection proved invariant is already guarded upstream. | **DISMISS_FALSE_POSITIVE** (Suppressed from PR review comments; logged for accuracy calibration). |

### 6.2 The Three-Step Test Integrity Filter

A failed test alone does not prove a defect. Invariant enforces three verification gates:
1. **Syntax & AST Pre-check**: Candidate test commands and scripts are parsed through AST verification before sandbox execution.
2. **Execution Watchdog & Error Separation**: Harness crashes, missing modules, and execution timeouts are categorized as `TIMEOUT_OR_CRASH` $\rightarrow$ `Inconclusive`, preventing tool failure from being misreported as product defects.
3. **Differential Grounding**: Tests are cross-referenced with `INVARIANT.md` specifications to ensure assertions reflect legitimate product contracts rather than hallucinated requirements.

### 6.3 REST and MCP Interfaces

* **REST API**:
  - `POST /api/v1/intelligence/evaluate`: Ingests a `SuspectedIssue` and returns a `VerifiedClassificationResult` with reasoning, evidence, and suggested action.
  - `GET /api/v1/intelligence/taxonomy`: Returns the full 5-tier classification schema and evidentiary definitions.
* **Model Context Protocol (MCP)**:
  - Tool: `invariant_evaluate_suspected_issue` available via stdio server for IDE integration (VS Code, Cursor, Windsurf).
